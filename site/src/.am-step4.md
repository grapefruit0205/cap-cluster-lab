## A 작업 순서

**시나리오:** 아직 세 대는 프로그램만 설치된 서버입니다. 마스터에서 클러스터를 만들고, 워커를 가입시킨 뒤, Pod 네트워크를 연결합니다.

| 순서 | 새로 생기는 것 | 정상적인 중간 상태 |
| --- | --- | --- |
| init | API Server, etcd, 인증서, 관리자 kubeconfig | 마스터 NotReady 가능 |
| join | 워커의 노드 등록과 kubelet 설정 | 노드 세 대가 보이지만 NotReady 가능 |
| CNI 설치 | Pod IP 할당과 노드 간 네트워크 | 세 노드 Ready, DNS 동작 |

**세 가지 주소:** API Server는 `10.20.1.10:6443`, Pod는 `10.11.x.x`, Service는 `10.96.x.x`를 사용합니다. Service IP는 EC2에 붙인 IP가 아닌 클러스터의 가상 주소입니다.

**AWS에서 VXLAN을 쓰는 이유:** Pod 패킷을 노드 IP 패킷 안에 넣어 전달합니다. 같은 서브넷에서도 캡슐화하므로, EC2가 Pod IP 패킷을 그대로 전달해야 하는 상황을 피합니다.

```flow TB
(③ 완료) -> kubeadm init
kubeadm init -> 워커 join
워커 join -> Calico 설치
Calico 설치 -> (⑤ 검증·채점)
```

## B 클러스터 초기화 (태스크 10 — 마스터에서만)

**왜 하는가:** 컨트롤 플레인과 인증서를 만들어 클러스터의 기준점을 세웁니다.

**한 줄씩 실행합니다.** *(cap-master)*:

```bash
sudo -i
hostname
kubeadm init --pod-network-cidr=10.11.0.0/16 --apiserver-advertise-address=10.20.1.10
```

**명령어 해석:**

- `kubeadm init` — 컨트롤 플레인(API Server · etcd · 스케줄러 · 컨트롤러 매니저)을 설치하고 클러스터를 만듭니다.
- `--pod-network-cidr=10.11.0.0/16` — Pod가 쓸 IP 대역입니다. ④의 Calico 설정과 같은 값이어야 합니다.
- `--apiserver-advertise-address=10.20.1.10` — 워커에게 API Server 위치를 알릴 주소입니다. 반드시 **프라이빗 IP**입니다.

! **주의:** `hostname`이 `cap-master`인지 먼저 확인하세요. EC2의 퍼블릭 IP는 OS 인터페이스에 없으므로 지정하면 바인드에 실패합니다.

**예상 출력:** 마지막에 `Your Kubernetes control-plane has initialized successfully!`와 `kubeadm join 10.20.1.10:6443 --token ...` 형태가 나오면 성공입니다.

! **경고:** 출력된 `kubeadm join` 명령의 토큰과 해시는 **교육생마다 다릅니다.** 본인 화면의 값을 메모장에 복사해 두세요. 놓쳤다면 `kubeadm token create --print-join-command`로 다시 만들 수 있습니다.

**kubectl 설정 + 노드 확인:**

```bash
mkdir -p $HOME/.kube
cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
chown $(id -u):$(id -g) $HOME/.kube/config
kubectl get nodes
kubectl describe node cap-master | grep -i taints
```

**명령어 해석:**

- `admin.conf` — 클러스터 관리자 인증서와 API Server 주소가 담긴 kubeconfig입니다.
- `cp -i` — 같은 파일이 있으면 덮어쓸지 물어봅니다.
- `chown $(id -u):$(id -g)` — 파일 소유자를 현재 사용자 UID·GID로 맞춥니다. 이 실습은 `sudo -i` 상태라 root 소유로 유지됩니다.
- `describe node ... | grep -i taints` — 노드에 붙은 taint(배치 제한)를 확인합니다.

**예상 출력:** `cap-master   NotReady   control-plane   ...` — `NotReady`는 CNI가 아직 없기 때문이며 이 시점에서는 정상입니다.

! **주의:** taint(`node-role.kubernetes.io/control-plane:NoSchedule`)는 kubeadm init이 자동으로 붙인 것입니다. 인터넷 자료에 자주 나오는 taint 제거 명령은 **실행하지 마세요.** 이후 장의 배치 설명과 채점이 이 taint를 전제로 합니다. `Taints: <none>`으로 보이면 아래 명령으로 복구합니다:

```bash
kubectl taint nodes cap-master node-role.kubernetes.io/control-plane:NoSchedule
```

**명령어 해석:** `NoSchedule`은 해당 taint를 허용하는 toleration이 없는 새 Pod의 배치를 막습니다. 이미 실행 중인 Pod를 강제로 내보내는 설정은 아닙니다.

**자동 완성과 별칭:**

```bash
apt install -y bash-completion
echo 'source <(kubectl completion bash)' >> ~/.bashrc
echo 'alias k=kubectl' >> ~/.bashrc
echo 'complete -o default -F __start_kubectl k' >> ~/.bashrc
source ~/.bashrc
k get ns
```

**명령어 해석:**

- `kubectl completion bash` — 탭 자동 완성 스크립트를 출력합니다. `<( )` 프로세스 치환으로 즉시 읽어 들입니다.
- `~/.bashrc`에 추가하면 세션마다 자동으로 적용됩니다.
- `alias k=kubectl` — 짧은 별칭을 만듭니다. `complete -F ...`로 k에도 완성을 연결합니다.

## C 워커 조인 (태스크 11 — 각 워커에서)

**왜 하는가:** 워커를 클러스터에 등록해야 스케줄러가 그 노드에 Pod를 배치합니다.

각 워커에 세션 관리자로 접속한 뒤:

```bash
sudo -i
hostname
```

**예상 출력:** `cap-node1`(또는 `cap-node2`)이면 정상입니다.

단계 B에서 복사한 join 명령을 **한 줄로** 붙여넣어 실행합니다:

```bash
kubeadm join 10.20.1.10:6443 --token <본인_토큰> --discovery-token-ca-cert-hash sha256:<본인_해시>
```

**명령어 해석:**

- `--token` — 마스터에 자신을 등록할 임시 인증 값입니다. 유효 기간은 보통 24시간입니다.
- `--discovery-token-ca-cert-hash` — 연결한 API Server가 진짜인지 CA 인증서로 검증하는 해시입니다.
- 이 두 값으로 워커가 안전하게 클러스터에 조인합니다.

! **주의:** root 권한이 없으면 `[ERROR IsPrivilegedUser]: user is not running as root`가 납니다. 줄 끝의 `\`는 Bash의 줄 연결 문법입니다. `>`는 다음 줄을 기다리는 표시입니다. 복사 실수를 줄이려면 본인의 join 명령을 한 줄로 붙여넣으세요.

**예상 출력:** `This node has joined the cluster: ...`가 나오면 성공입니다.

**확인 (cap-master):**

```bash
kubectl get nodes
```

**예상 출력:** 세 노드가 모두 보이면 정상입니다. 아직 `NotReady`입니다.

## D Calico 설치 (태스크 12 — 마스터)

**왜 하는가:** CNI가 없으면 노드가 NotReady로 남고 Pod 사이 통신도 되지 않습니다.

**CRD와 Tigera Operator 설치** — CRD 파일이 커서 `kubectl apply`는 `metadata.annotations: Too long` 오류가 날 수 있습니다. 반드시 `kubectl create`를 사용합니다:

```bash
kubectl create -f https://raw.githubusercontent.com/projectcalico/calico/v3.32.1/manifests/v1_crd_projectcalico_org.yaml
kubectl create -f https://raw.githubusercontent.com/projectcalico/calico/v3.32.1/manifests/tigera-operator.yaml
```

**명령어 해석:**

- CRD — 커스텀 리소스(예: Calico의 IPPool)의 자료형 정의입니다.
- Tigera Operator — Calico 자체를 설치·운영하는 컨트롤러입니다.
- `create`는 새 오브젝트를 만들며, 같은 이름이 이미 있으면 실패합니다. 일반적인 client-side `apply`는 큰 CRD의 annotation 크기 제한에 걸릴 수 있습니다. server-side apply도 있지만 이 교안은 `create`로 통일합니다.

**설정 파일 수정** — Pod CIDR과 캡슐화 모드를 바꿉니다:

```bash
mkdir -p ~/cni && cd ~/cni
curl -fsSLO https://raw.githubusercontent.com/projectcalico/calico/v3.32.1/manifests/custom-resources.yaml
sed -i 's|192.168.0.0/16|10.11.0.0/16|; s|encapsulation: VXLANCrossSubnet|encapsulation: VXLAN|' custom-resources.yaml
grep -E "cidr:|encapsulation:" custom-resources.yaml
```

**명령어 해석:**

- `curl -fsSLO` — 원격 파일을 같은 이름으로 저장합니다.
- `sed` 치환 2개 — 첫 치환은 Pod 대역을 `kubeadm init`의 값과 같게, 둘째 치환은 캡슐화 모드를 VXLAN으로 바꿉니다.
- `grep -E "cidr:|encapsulation:"` — 두 값이 바뀌었는지 확인합니다.

**예상 출력:** `cidr: 10.11.0.0/16`과 `encapsulation: VXLAN`이면 정상입니다.

! **경고:** 기본값 `VXLANCrossSubnet`은 같은 서브넷 노드끼리 캡슐화하지 않고 Pod IP를 그대로 보냅니다. EC2는 **Source/Destination Check**가 켜져 있어 자기 IP가 아닌 Pod IP 패킷을 폐기하므로, 노드 간 Pod 통신과 CoreDNS가 조용히 실패합니다. `VXLAN`으로 바꾸면 바깥 헤더에 노드 IP가 실려 정상 전달됩니다.

**적용 + Pod 확인** (2~5분, `Ctrl+C`로 종료):

```bash
kubectl create -f custom-resources.yaml
kubectl get pods -n calico-system -w
```

**명령어 해석:**

- `custom-resources.yaml` — Calico가 쓸 IPPool(Pod CIDR) 등을 정의합니다.
- `kubectl get pods -w` — 변경을 실시간 감시(watch)합니다. `Ctrl+C`로 나옵니다.

**예상 출력:** 모든 Pod가 `Running`이면 `Ctrl+C`로 빠져나옵니다. APIServer · Goldmane · Whisker 관련 Pod가 추가로 보일 수 있지만 모두 `Running`이면 정상입니다.

**노드 상태 확인:**

```bash
kubectl get nodes -o wide
```

**명령어 해석:**

- `-o wide` — INTERNAL-IP, CONTAINER-RUNTIME 같은 추가 열을 함께 보여 줍니다.

**예상 출력:** 세 노드가 모두 `Ready`이면 클러스터 구축이 완료된 것입니다.

**참고:** 8장에서 requests를 계산할 때 쓰는 노드별 할당 가능 자원도 확인해 둡니다:

```bash
kubectl get nodes -o custom-columns=NAME:.metadata.name,CPU:.status.allocatable.cpu,MEMORY:.status.allocatable.memory
```

**명령어 해석:**

- `-o custom-columns` — 원하는 JSON 경로를 열로 뽑아 표를 만듭니다. 여기서는 할당 가능한 CPU · 메모리입니다.
