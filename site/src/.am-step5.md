이 페이지는 [④ 클러스터 초기화·CNI](lab02-step4.html)에 이어 노드 간 Pod 통신과 DNS를 검증하고, CloudShell에서 AWS 리소스 채점을 실행합니다.

## A 작업 순서

**시나리오:** 쇼핑몰을 배포하기 전에 플랫폼 팀이 환경을 인계합니다. 노드가 Ready인 것만 확인하지 말고, 실제 애플리케이션 통신과 DNS도 시험합니다.

| 검사 | 증명하는 것 | 증명하지 못하는 것 |
| --- | --- | --- |
| 노드 Ready | kubelet이 노드 준비 상태를 보고함 | 모든 Pod 사이의 통신 성공 |
| 다른 노드 Pod에 HTTP 200 | 해당 경로의 Pod 네트워크와 nginx 응답 | 모든 통신 경로의 무결성 |
| Service DNS 조회 | 클러스터 내부 이름 해석 | 외부 인터넷 DNS 전체 |
| AWS 채점 10/10 | 스크립트가 검사하는 AWS 설정 | Kubernetes 전체 정상 동작 |

**인계 기준:** 세 노드 Ready + 다른 워커 간 HTTP 200 + DNS `10.96.0.1` + AWS 채점 통과를 함께 확인합니다.

```flow TB
(④ 완료) -> 구성요소 확인
구성요소 확인 -> Pod 간 통신 검증
Pod 간 통신 검증 -> DNS 확인
DNS 확인 -> CloudShell 채점
CloudShell 채점 -> (완료)
```

## B 클러스터 동작 검증 (태스크 13 — cap-master)

**1장에서 배운 구성요소를 직접 확인:**

```bash
ls /etc/kubernetes/manifests
kubectl get pods -n kube-system -o wide
```

**명령어 해석:**

- `/etc/kubernetes/manifests` — kubelet이 직접 실행하는 static pod 매니페스트 폴더입니다. 컨트롤 플레인 4종이 여기 있습니다.
- `-o wide` — NODE 열까지 함께 봅니다. 어느 노드에서 뭘 돌고 있는지 확인합니다.

**예상 출력:** Static Pod 매니페스트 4개(etcd · kube-apiserver · kube-controller-manager · kube-scheduler), 이름 끝이 `-cap-master`인 Pod 4개, kube-proxy 3개, coredns 2개가 보이면 정상입니다.

**서로 다른 노드의 Pod 사이 통신 검증:**

```bash
kubectl create deployment pingtest --image=nginx --replicas=4
kubectl rollout status deployment pingtest --timeout=180s
kubectl get pods -l app=pingtest -o wide
POD_A=$(kubectl get pod -l app=pingtest --field-selector spec.nodeName=cap-node1 -o jsonpath='{.items[0].metadata.name}')
POD_B_IP=$(kubectl get pod -l app=pingtest --field-selector spec.nodeName=cap-node2 -o jsonpath='{.items[0].status.podIP}')
kubectl exec $POD_A -- curl -s -o /dev/null -w "%{http_code}\n" http://$POD_B_IP
```

**명령어 해석:**

- `create deployment` — nginx 4개짜리 검증용 배포를 만듭니다.
- `rollout status --timeout=180s` — 배포가 끝날 때까지 대기합니다. 180초 안에 끝나지 않으면 실패로 봅니다.
- `-l app=pingtest` — 라벨 셀렉터로 이 배포의 Pod만 봅니다.
- `--field-selector spec.nodeName=` — **어느 노드에 떴는지** 조건으로 Pod를 고릅니다.
- `-o jsonpath='{...}'` — Pod 이름 또는 Pod IP만 정확히 뽑아 변수에 저장합니다.
- `kubectl exec ... -- curl` — 파드 A **안에서** 파드 B의 IP로 HTTP 요청을 보냅니다.
- `-o /dev/null -w "%{http_code}"` — 응답 본문은 버리고 HTTP 상태 코드만 인쇄합니다.

**예상 출력:** Pod IP가 `10.11.x.x` 대역이고 마지막 줄이 `200`이면 노드 간 Pod 네트워크가 정상입니다.

**참고:** replicas=4는 두 워커로의 분산을 보장하지 않습니다. 변수 추출 전에 NODE 열에서 양쪽 워커에 Pod가 있는지 확인하세요. 한쪽에만 있다면 아래처럼 검증용 배포에 필수 Pod anti-affinity를 추가합니다.

```bash
kubectl patch deployment pingtest --type=merge -p '{
  "spec": {
    "replicas": 2,
    "strategy": {"type": "Recreate", "rollingUpdate": null},
    "template": {"spec": {"affinity": {"podAntiAffinity": {
      "requiredDuringSchedulingIgnoredDuringExecution": [{
        "labelSelector": {"matchLabels": {"app": "pingtest"}},
        "topologyKey": "kubernetes.io/hostname"
      }]
    }}}}
  }
}'
kubectl rollout status deployment pingtest --timeout=180s
kubectl get pods -l app=pingtest -o wide
```

**명령어 해석:** replicas를 2로 줄이고, 같은 hostname에 `app=pingtest` Pod가 함께 배치되지 못하게 합니다. `Recreate`는 기존 검증용 Pod를 먼저 내려 교체 공간 문제를 피합니다. 정상 워커가 둘이면 한 개씩 배치됩니다. NODE 열을 확인한 뒤 위의 `POD_A`, `POD_B_IP`, `curl` 세 줄을 다시 실행합니다. 계속 Pending이면 워커 상태와 Pod Events를 확인합니다.

**클러스터 DNS 확인 + 검증용 리소스 정리:**

```bash
kubectl exec $POD_A -- getent hosts kubernetes.default.svc.cluster.local
kubectl delete deployment pingtest
```

**명령어 해석:**

- `getent hosts` — 파드 안에서 클러스터 DNS 이름을 해석해 봅니다. CoreDNS가 동작하는지 확인합니다.
- `kubectl delete deployment` — 검증이 끝난 리소스를 지웁니다. 파드는 같이 사라집니다.

**예상 출력:** `10.96.0.1`로 해석되면 CoreDNS가 정상입니다. 검증용 리소스는 지웁니다.

## C AWS 리소스 채점 (태스크 14 — CloudShell)

📍 **주의:** CloudShell에서는 `verify-aws.sh`만 실행합니다. 클러스터 채점은 cap-master 노드 셸에서 실행합니다.

```bash
cd ~
git clone https://github.com/worldvit/k8s-labs-7days.git 2>/dev/null || (cd k8s-labs-7days && git pull)
bash ~/k8s-labs-7days/lab02-install/verify-aws.sh
```

**명령어 해석:**

- `git clone ... || (cd ... && git pull)` — clone 실패 시 기존 폴더에서 pull을 시도합니다. 네트워크 오류도 실패 원인이므로 출력과 종료 상태를 확인합니다. 로컬 수정이 있으면 pull이 충돌할 수 있습니다.
- `bash .../verify-aws.sh` — aws CLI로 VPC · 서브넷 · 보안 그룹 · 인스턴스 · 태그를 검사해 PASS/FAIL을 인쇄합니다.

**예상 출력:** 검사 항목 10개가 모두 `PASS`이고 `결과: 10/10  통과`이면 정상입니다.

- VPC cap-vpc (10.20.0.0/16)
- 퍼블릭 서브넷 2개 · 서로 다른 AZ
- 보안 그룹 자기 참조 규칙 · 0.0.0.0/0 인바운드 없음
- 인스턴스 3대 실행 중 · 동일 AZ · 고정 프라이빗 IP
- IAM 인스턴스 프로파일 · 메타데이터 홉 제한 2 이상
- 공통 태그 Project=capstone · Owner=cap

## D FAIL일 때 되돌아갈 단계

| 검사 항목 | 돌아갈 단계 |
| --- | --- |
| API Server 접근 · 노드 등록 | ④ 태스크 10~11 |
| cap-master control-plane taint 유지 | `kubectl taint nodes cap-master node-role.kubernetes.io/control-plane:NoSchedule` 실행 후 재채점 |
| 노드 Ready · Calico · CoreDNS | ④ 태스크 12 |
| 런타임 containerd 2.x | ② 태스크 7 |
| VPC · 서브넷 | ① 태스크 1 |
| 보안 그룹 | ① 태스크 2 |
| 인스턴스 AZ · IP · 프로파일 · 홉 제한 | ① 태스크 4 · ③ 태스크 9.3 |
| 태그 | 아래 태그 진단 |

**태그 FAIL 진단 + 일괄 추가 (CloudShell)** — 이미 있는 태그는 같은 값으로 덮어쓰므로 여러 번 실행해도 안전합니다:

```bash
source ~/cap-k8s.env
aws ec2 describe-instances --filters "Name=tag:Name,Values=cap-master,cap-node1,cap-node2" Name=instance-state-name,Values=running \
  --query 'Reservations[].Instances[].[Tags[?Key==`Name`].Value|[0],Tags[?Key==`Project`].Value|[0],Tags[?Key==`Owner`].Value|[0]]' \
  --output table --region $REGION
IDS=$(aws ec2 describe-instances --filters "Name=tag:Name,Values=cap-master,cap-node1,cap-node2" Name=instance-state-name,Values=running \
  --query 'Reservations[].Instances[].InstanceId' --output text --region $REGION)
echo "대상: $IDS $VPC_ID"
```

**대상 확인:** 출력에 본인 실습 인스턴스 `i-` ID 3개와 `vpc-` ID 1개가 맞는지 확인한 뒤, 아래 변경 명령을 따로 실행합니다.

```bash
aws ec2 create-tags --resources $IDS $VPC_ID --tags Key=Project,Value=capstone Key=Owner,Value=cap --region $REGION
bash ~/k8s-labs-7days/lab02-install/verify-aws.sh
```

**명령어 해석:**

- 첫 `describe-instances` — 어느 인스턴스에 Project · Owner 태그가 빠졌는지 표로 확인합니다(None 칸).
- `IDS=$(...)` — 세 인스턴스의 ID를 한 변수에 모읍니다.
- `create-tags --resources $IDS $VPC_ID` — 인스턴스 3대와 VPC에 같은 태그를 한 번에 붙입니다.
- 마지막 줄의 재채점은 붙인 태그가 즉시 반영되는지 다시 확인합니다.

! **주의:** `대상:` 줄에 `vpc-`가 없으면 `source ~/cap-k8s.env`를 빠뜨린 것입니다.

## E 완료 및 클러스터 유지

- 노드 간 Pod 통신(HTTP 200) · 클러스터 DNS 검증 완료
- AWS 리소스 채점 10/10 통과 완료

**이 클러스터는 누적 실습의 기반이므로 삭제하지 마세요.** 수업 종료 시 강사가 안내하면 콘솔 EC2 → 인스턴스에서 세 노드를 **중지**합니다. 중지 후 다시 시작하면 퍼블릭 IP는 바뀌지만 고정 프라이빗 IP와 Session Manager(인스턴스 ID 기반) 덕분에 클러스터는 유지됩니다. 다음은 2일차 Lab03에서 이 클러스터에 첫 Pod를 배포합니다.

**비용:** 인스턴스를 중지해도 EBS 볼륨과 AMI 스냅샷 같은 저장 공간 비용은 남습니다. 중지와 삭제는 다릅니다.
