이 페이지는 [② 마스터에 공통 기반 설치](lab02-step2.html)에 이어 공통 기반을 AMI로 만들고 워커 2대를 시작합니다.

## A 작업 순서

**시나리오:** 공통 프로그램은 같아야 하지만 서버의 신원까지 같아지면 안 됩니다. AMI로 패키지와 설정을 복제하고, 새 인스턴스마다 이름·AWS 권한 연결·태그를 다시 지정합니다.

| AMI에 담는 것 | 새 인스턴스에서 따로 설정할 것 | 담으면 안 되는 상태 |
| --- | --- | --- |
| OS, containerd, Kubernetes 패키지 | 프라이빗 IP, IAM 프로파일, SG | init 이후의 클러스터 인증서 |
| 커널·시간·런타임 설정 | 태그, 메타데이터 옵션, 고유 hostname | 마스터의 etcd 데이터 |

**통과 기준:** 각 인스턴스가 SSM에 별도로 Online이고, hostname이 서로 달라야 합니다. 이름은 EC2의 Name 태그가 아니라 OS의 `hostname`을 확인합니다.

```flow TB
(② 완료) -> 복제 전 정리
복제 전 정리 -> AMI 생성
AMI 생성 -> 워커 2대 시작
워커 2대 시작 -> 워커 호스트 이름
워커 호스트 이름 -> (④ 클러스터 초기화)
```

## B 복제 전 정리 (태스크 9.1)

**왜 하는가:** 같은 신원이 복제되면 SSM 등록과 노드 이름이 충돌합니다.

! **경고:** AMI는 반드시 **kubeadm init 전에** 만듭니다. 초기화된 클러스터 상태(/etc/kubernetes, /var/lib/etcd)가 들어간 AMI로 워커를 만들면 인증서와 etcd 데이터가 복제되어 클러스터가 깨집니다.

*(cap-master, sudo -i 상태)* 아래는 교안의 정리 명령입니다. **실행 전에 주의사항을 먼저 읽으세요.** 에이전트를 정지하면 현재 관리 연결이 끊길 수 있습니다.

```bash
snap stop amazon-ssm-agent
rm -rf /var/lib/amazon/ssm/i-*
truncate -s 0 /etc/machine-id
cloud-init clean --logs
echo "cleanup done"
```

**명령어 해석:**

- `snap stop` — SSM 에이전트를 정지합니다. 정지만으로 등록 정보가 삭제되지는 않습니다.
- `rm -rf /var/lib/amazon/ssm/i-*` — 이 인스턴스 ID로 남은 등록 파일을 지웁니다.
- `truncate -s 0` — machine-id 파일을 0바이트로 비웁니다. 다음 부팅 때 새 ID가 만들어집니다.
- `cloud-init clean --logs` — cloud-init의 상태와 로그를 초기화합니다. 다음 부팅에서 처음처럼 실행됩니다.

! **주의:** 세션이 끊겼다면 이후 명령의 완료를 보장할 수 없습니다. `cleanup done`을 보지 못한 상태를 성공으로 간주하지 마세요. 강사에게 SSM 세션과 독립적으로 실행되는 이미지 정리 절차를 확인하고, 정리 완료 확인 후 AMI를 만듭니다.

💭 machine-id와 SSM 등록 정보는 인스턴스마다 달라야 합니다. 비워 둔 machine-id는 다음 부팅 때 새로 만들어집니다.

## C AMI 생성 (태스크 9.2)

**왜 하는가:** 공통 기반 설치를 반복하지 않고 워커를 같은 구성으로 만들기 위해서입니다.

**콘솔:** EC2 → 인스턴스 → `cap-master` 선택 → **작업** → **이미지 및 템플릿** → **이미지 생성**에서:

| 항목 | 값 |
| --- | --- |
| 이미지 이름 | cap-k8s-base-1.36 |
| 설명 | kubeadm 1.36 + containerd 2.x base |
| 재부팅 | 체크된 상태로 둠 |
| 태그 | Project=capstone · Owner=cap |

왼쪽 메뉴 **AMI**에서 `cap-k8s-base-1.36`의 상태가 **사용 가능(available)**이 될 때까지 기다립니다. (5~10분)

**참고:** 이미지 생성 중 `cap-master`가 재부팅됩니다. 재부팅 후 SSM 에이전트는 자동으로 다시 시작되므로 따로 켤 필요가 없습니다.

## D 워커 2대 시작 (태스크 9.3)

**왜 하는가:** 워커가 있어야 Pod를 실제로 배치하고 스케줄 결과를 확인할 수 있습니다.

**콘솔:** AMI 목록에서 `cap-k8s-base-1.36` 선택 → **AMI로 인스턴스 시작**. `cap-node1`을 먼저 만들고, 같은 방법으로 `cap-node2`를 만듭니다.

| 항목 | cap-node1 | cap-node2 |
| --- | --- | --- |
| 태그 | Name=cap-node1 · Project=capstone · Owner=cap | Name=cap-node2 · Project=capstone · Owner=cap |
| 인스턴스 유형 | m7i-flex.large | 동일 |
| 키 페어 | 키 페어 없이 계속 진행 | 동일 |
| VPC · 서브넷 | cap-vpc · cap-subnet-public1-ap-northeast-2a | 동일 |
| 퍼블릭 IP 자동 할당 | 활성화 | 동일 |
| 보안 그룹 | cap-k8s-node-sg | 동일 |
| 기본 IP | 10.20.1.11 | 10.20.1.12 |
| 스토리지 | 30 GiB gp3 | 동일 |
| IAM 인스턴스 프로파일 | cap-k8s-node-role | 동일 |
| 메타데이터 액세스 가능 | 활성화 | 동일 |
| 메타데이터 버전 · 홉 제한 | V2 전용 · 2 | 동일 |

! **주의:** IAM 인스턴스 프로파일, 메타데이터 홉 제한, **태그**는 **AMI에 들어가지 않는 인스턴스 속성**입니다. AMI에 붙인 Project · Owner 태그도 복사되지 않습니다. 워커를 시작할 때 세 가지 모두 반드시 다시 지정하세요.

! **경고:** **기본 IP도 AMI에 들어가지 않습니다.** 워커마다 `10.20.1.11`, `10.20.1.12`를 직접 입력하세요. 관련 칸은 **네트워크 설정 → 편집 → 고급 네트워크 구성 → 기본 IP**입니다. 비워두면 DHCP가 임의 주소를 주고, `/etc/hosts`와 실제 IP가 어긋나 ping과 join이 실패합니다.

**증상:** 워커에서 `ping cap-master`가 `Destination Host Unreachable`이고 출발지가 `10.20.1.x`가 아니면 이 문제입니다. 각 노드에서 `hostname -I`로 확인하세요.

**확인 (CloudShell, 시작 후 2~3분 뒤):**

```bash
source ~/cap-k8s.env
aws ec2 describe-instances --filters "Name=tag:Name,Values=cap-*" Name=instance-state-name,Values=running \
  --query 'Reservations[].Instances[].[Tags[?Key==`Name`].Value|[0],PrivateIpAddress,Placement.AvailabilityZone,MetadataOptions.HttpPutResponseHopLimit]' \
  --output table --region $REGION
aws ssm describe-instance-information --query 'InstanceInformationList[].[InstanceId,PingStatus]' --output table --region $REGION
```

**명령어 해석:**

- `--filters "Name=tag:Name,Values=cap-*"` — 이름 태그가 `cap-`으로 시작하는 인스턴스만 거릅니다. `*`는 와일드카드입니다.
- ``Tags[?Key==`Name`].Value|[0]`` — 태그 목록에서 Key가 Name인 것의 첫 값을 뽑습니다(JMESPath 필터).
- 두 번째 명령은 SSM 등록 상태(Online)를 그대로 봅니다.

**예상 출력:** 세 노드가 같은 AZ에 있고 홉 제한이 모두 `2`이며, 두 번째 표에서 세 인스턴스가 `Online`이면 정상입니다.

## E 워커 호스트 이름 (태스크 9.4)

**왜 하는가:** 노드 이름이 겹치면 클러스터가 여러 노드를 하나로 착각합니다.

각 워커에 세션 관리자로 접속합니다. `cap-node1` 먼저:

```bash
sudo -i
hostname
hostnamectl set-hostname cap-node1
reboot
```

**명령어 해석:**

- `hostname` — 접속하자마자 어느 노드인지 확인합니다.
- `hostnamectl set-hostname` — AMI에 복제된 `cap-master` 이름을 워커 이름으로 바꿉니다.

**예상 출력:** 첫 `hostname`은 `cap-master`로 나옵니다(AMI에 복제된 값). 재접속 후 `hostname`이 `cap-node1`이면 정상입니다.

`cap-node2`에도 같은 방법으로 `hostnamectl set-hostname cap-node2` 후 재부팅합니다.

! **경고:** 이 단계를 잊으면 워커 두 대의 이름이 모두 `cap-master`가 되어 kubeadm join이 실패하거나 노드가 서로 덮어씁니다. 세션에 들어가면 **항상 hostname부터** 확인하세요.

**노드 간 통신 확인** (각 워커에서, 재접속 후):

```bash
hostname
ping -c 2 cap-master
```

**명령어 해석:**

- `ping -c 2` — 2번만 응답을 보고 멈춥니다. `/etc/hosts`에 등록한 `cap-master` 이름으로 요청합니다.
- 0% 손실이면 같은 보안 그룹끼리 허용하는 자기 참조 규칙이 동작하는 것입니다.

**예상 출력:** `0% packet loss`면 보안 그룹 자기 참조 규칙이 동작하는 것입니다.
